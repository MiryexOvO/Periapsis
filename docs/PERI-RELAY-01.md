# PERI 原生发布与 Relay 实验

`peri-native` 提供原生 QUIC 主动发布 API 和单资源 Relay 库。
另提供 [原生分进程服务命令](PERI-SERVICE-01.md)，尚无推流软件插件或浏览器接入。

## 主动发布

在原生实验 ALPN `peri-dev-02` 的控制流上新增 `peri.publish`：

```json
{"type":"peri.publish","resource":"live/av1","hello":{"version":1,"profiles":["live"],"codecs":["video/av1"],"extensions":[]}}
```

前导、长度封装、`peri.accept` 与 `peri.ack` 沿用原生线协议。
发布者使用 `publish` 发起；接入端使用 `accept_publish` 接受。
发布者发送媒体单向流，接入端读取；ACK 规则与订阅模式一致。
原有 `subscribe` / `accept` 则由服务端发送媒体。
两类接入 API 严格拒绝对方的请求类型；不能仅通过交换端点标签获得发布权限。

这是新增消息，不改变既有对象头与订阅消息。旧实现可以拒绝未知发布请求，
不宣称新增 API 与所有早期实现互通。连接身份、证书信任及资源授权仍由调用方负责，
消息类型和资源名称不提供身份认证；受保护服务另使用角色凭据并拒绝匿名接入。

## Relay 库

1. 接入端完成 `accept_publish`，用 media `Subscriber::new` 校验发布目录。
2. 使用该目录构建 `Relay`，调用 `ingest` 接收一个发布生命周期。
3. 对每个已授权的下游连接完成 `accept`，交给 `serve` 分发。

目录不可变，每实例只允许一次 ingest；重新推流需要创建新实例。
发布出错、空闲超过调用方预算或 ingest 任务取消，资源关闭并取消全部下游。
订阅者退出会注销自己的队列。显式 `close` 同样取消全部下游。

当前 ingest 要求**整个资源的序号严格递增**，依赖必须已在同轨道出现且仍在最近
128 个非 Disposable 参考项中；异常导致资源关闭。尚无并发上游乱序重排；关键帧请求经保留控制流转发，详见[播放说明](PERI-PLAYBACK-01.md)。

恢复请求及接收报告现在通过事件唤醒Relay的分发与接入循环，不再依赖下一帧或发送确认完成后才轮询。
接入端等待媒体时保留同一个读取future，反馈唤醒不取消半个对象、不重启原有接收预算。
通知只表示邮箱可能变化，实际请求仍受8条队列限制、报告仍合并为最新值；没有新增轮询定时器或每帧后台任务。
控制流写入仍有原来的超时与频率限制，正在进行的对象写入也可能延后反馈处理，因此不承诺立即响应或端到端时限。
单观看者报告上行策略、多观看者作用域隔离、鉴权与对象封装保持原语义。
原生对象 API 本身允许并发，接入此 Relay 的发布者需自行保证交付顺序。

Relay 不解码、不转码，保持目录、时间戳、依赖和编码负载。
每个下游从独立单元开始；没有 GOP 缓存，晚加入通常需要等待下一个关键帧。
若依赖未曾转发或对象在 Relay 内已过期，跳过该对象；参考链受损时按轨道等待独立单元。
下游按原顺序排队写入对象，但最多并行等待 4 个传输确认，不逐帧等待 ACK 才写下一帧。
依赖表表示已排队的对象，不是交付确认；解码依赖仍由接收端 DecodeBuffer 与实际解码器管理。
发送名额满、缺少依赖或对象过期时跳过该对象；参考链受损后等待新的独立单元。
单对象发送超时、RESET/STOP(1) 不再主动结束订阅连接；其他错误仍结束连接。
旧 GOP 的迟到失败不会清除已经排队的新恢复点。队列溢出仍会断开慢订阅者。

## 资源与时间边界

默认最多 8 个订阅者，每个队列 8 帧，每帧最多 1 MiB − 68 字节，驻留预算 300 ms。
Limits 可配置，上限为 64 订阅者、128 排队帧、1 秒驻留，但还必须满足：

```text
viewers × (queued_frames + 4) × frame_bytes ≤ 128 MiB
```

该式是排队及当前发送的编码负载保守上界，元数据、目录、网络窗口和复制缓冲另计。
转发使用共享编码负载引用；写入协议时仍可能复制，不宣称端到端零复制。
队列满会取消该订阅者；发布端不等待慢订阅者。单对象超时仅取消对象并使受影响参考链进入恢复。

每个对象的 Relay 截止时间从接入端**收完该对象**开始，取配置驻留和下游协商最大
缓冲时间的较小值；排队和发送确认共用剩余时间。该预算不包含上游网络、编码、
解码与显示，不能作为采集到显示延迟。每个下游依次写入、并行等待最多 4 个确认；
高 RTT 下仍受窗口大小、对象大小、接收顺序和媒体依赖限制。

## 真实 AV1 验证示例

需要 Rust 与支持 libaom-av1 编码、AV1 解码的 FFmpeg：

```powershell
cargo run -p peri-relay --example relay_video
```

通过 `PERI_FFMPEG` 指定 FFmpeg 路径。示例在本进程内建立发布端、Relay 与两个接收端，
使用本机真实 QUIC/TLS 连接；临时证书加入测试专用信任库，不关闭证书验证。

示例生成 320×180、15 fps、2 秒的 AV1 全关键帧片段，按媒体时间戳发送，
重建两个接收文件，并比较编码帧及 FFmpeg 解码后的逐帧校验值。
AV1 数据为 IVF 中的低开销 OBU 序列；片段内携带序列头，本示例目录 init 为空。
输入由示例固定参数生成，不支持把任意外部 AV1 片段当成全关键帧输入。

输出位于被 Git 忽略的 `dist/native-relay/`。该示例验证内容保真和实际解码，
不提供实时观看 UI，也不是生产编码配置、真实采集、音视频同步或性能比较。

Relay 在本地超时、取消或跳过参考链时也会主动排队关键帧请求；实时编码响应见[实时测试源](PERI-LIVE-01.md)。

## 逐观看者字节配额与发送进度

Limits新增buffered_bytes；显式列出全部字段的接入方须补充此字段，使用..Limits::default()的调用方沿用默认值。
该额度覆盖Frame.payload在排队、待写入和待确认阶段的保留量。出队不释放额度；确认、失败或取消才释放。
它不包含Quinn、封装及修复缓冲，不应作为进程总内存上限。

Relay同时推进控制反馈、一个待写入操作和最多四个在途媒体操作；慢写入不阻塞恢复请求转发。
写入future跨反馈唤醒保留，使用入队时确定的绝对期限。每轮反馈处理有固定数量上限，避免持续控制流饿死媒体进度。
队列帧数与字节额度分别检查，任一耗尽时取消该观看者并释放其任务，其他观看者不受该额度影响。
