# PERI media-01 实验媒体配置

media-01 建立在 [原生对象线协议](PERI-WIRE-01.md) 之上，由 `peri_native::media` 实现。
底层 ALPN 和对象头不变；两端必须明确使用本配置的 API，不自动识别或回退到其他媒体格式。
当前没有动态媒体配置协商、编码配置更新、跨资源时间同步或网络恢复反馈消息。

## 初始目录

发布端建立 Session 后，由 `Publisher::new` 发送目录对象：

- sequence、timestamp_us、duration_us 均为 0，independent 为 true。
- payload 为 6 字节 ASCII `PCAT01`，后跟 UTF-8 JSON 目录。
- 完整 payload 不超过 16 KiB。此限制在对象收完后检查；底层收取仍受 1 MiB 上限约束。
- `Subscriber::new` 必须先校验该目录，随后才能接收媒体单元。

目录 JSON 只有 `tracks` 字段，包含 1–8 条轨道；未知字段拒绝。每条轨道含：

| 字段 | 类型与限制 |
| --- | --- |
| id | 非零 u16，会话内唯一 |
| kind | `video` 或 `audio` |
| codec | 必须属于会话协商所得编码集合，视频以 `video/` 开头，音频以 `audio/` 开头 |
| init | JSON 字节数组，最多 4096 字节，编码专属初始化数据 |
| width、height | 视频必填，1–8192；音频为 null |
| sample_rate | 音频必填，8000–192000；视频为 null |
| channels | 音频必填，1–8；视频为 null |

目录在会话内不可变，配置变化需重建会话。当前透传初始化数据；
编码专属字节布局及实际解码兼容性仍需进一步明确和验证，不能仅凭编码字符串认定能解码。
接收端必须保留总目录上限，不能将每轨道上限理解为总上限的替代。

## 媒体单元

继续使用原生对象头的全局 sequence、timestamp_us、duration_us 和 independent。
sequence 从 1 开始，在整个资源的所有轨道中唯一；duration_us 为 1–1,000,000。
各轨道时间戳共享发布端的媒体时间轴，不表示两端墙钟已经同步。

对象 payload 的媒体前缀为：

| 偏移 | 字段 |
| --- | --- |
| 0 | u8 kind：0 Key、1 Reference、2 Disposable、3 Audio |
| 1 | 大端 u16 track |
| 3 | u8 dependency_count，最多 8 |
| 4 | dependency_count 个大端 u64 依赖序号 |
| 后续 | 非空编码负载，最多 1 MiB − 68 字节 |

Key、Audio 必须不带依赖，外层 independent 为 true；Reference、Disposable 必须带依赖，
外层 independent 为 false。视频不能使用 Audio 类型，音频只能使用 Audio 类型。
依赖必须非零、无重复、小于当前序号且属于同轨道。不存在任意前向依赖和循环依赖。
独立投递仍需要正确的编码配置与解码器状态，不表示无需初始化便可解码。

Publisher/Subscriber 负责媒体结构与轨道校验，不执行实际解码。
解码依赖、重放窗口和截止时间由下述 DecodeBuffer 执行，调用方不能跳过它后仍声称已启用这些保护。

## 接收端解码缓冲

`DecodeBuffer::push(frame, now, deadline)` 接收本地单调时钟与播放截止时间。
实际截止时间为 `min(deadline, now + agreement.maxBufferMs)`。
调用方负责将媒体时间轴映射为本地播放时间；这不是网络在途时间或端到端延迟测量。

缓冲区同时限制排队编码负载字节与帧数。帧数包含排队及已提交但未确认解码的帧，最多 128。
`queued_bytes` 只统计排队的编码负载；初始化数据、元数据、网络缓冲和解码器持有内存另计。
已解码依赖最多保留 128 项。重放窗口覆盖最高已接纳序号之前的 128 个序号，
窗口内重复和窗口外旧单元拒绝；过大的序号跳跃可能导致迟到单元被拒绝。
窗口内未知依赖可以等待；已知跨轨依赖拒绝，依赖永远不到时最终过期。
编码器应避免将 Disposable 作为后续单元的解码依赖，因为它不会成为已解码参考项。

`next(now)` 优先处理过期状态，随后按截止时间选择依赖已经解码的单元：

- `Decode(frame)`：调用方提交解码，成功后调用 `decoded(sequence, now)`，其他单元才可依赖它。
- `Drop { sequence }`：丢弃过期 Disposable；若已提交解码，调用方还需忽略或取消其输出。
- `Recover { track }`：参考单元、关键帧或音频过期，需要轨道恢复。

网络收取完成不等于解码确认。迟到的解码确认会被拒绝；
迟到 Disposable 不清空参考链，其他类型迟到会使相关轨道进入恢复状态。
调用方解码失败时调用 `recover(track)`，同时清理该轨道解码器中的工作和输出。
恢复清除该轨道的已解码依赖和在途解码状态，丢弃排队的依赖帧，保留排队的独立恢复单元。
当没有独立单元时继续等待，调用方可以请求新的关键帧；当前没有自动网络反馈协议。

## 范围与验证边界

这是原生媒体格式和接收调度实现，不是完整播放器。已有原生主动发布和单资源 Relay，
见 [原生发布与 Relay 实验](PERI-RELAY-01.md)。AV1 示例验证实际编码和接收后解码。
实时解码播放、音画播放时钟映射、推流软件 SDK/插件、浏览器迁移与 MPQUIC 尚待完成。
原生对象接收目前仍按调用顺序串行读流，慢流由 I/O 预算限制；本模块不修复其潜在等待。
单元测试中的媒体数据用于封装与调度验证；AV1 示例另做真实解码验证，尚无画质收益结论。
