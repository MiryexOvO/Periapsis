# 亚秒目标与测量口径

PERI 的研发目标为低于 1000 ms，目标不等于现有实现已经达标。
必须同时报告持续播放延迟、首帧等待、弱网冻结和恢复；不能用单项低延迟覆盖多秒中断。

当前 `native:live:check` 增加同机软件输入到输出测量：

- source_input：Rust 向实时合成编码工作进程提交一帧前。
- frame_output：真实解码与本地调度完成后；显示模式为 RGB 写入显示进程完成，headless 没有物理显示。
- 按同一发布生命周期的帧序号配对，报告匹配数、P50、P95、最大值和负墙钟样本数。
- 至少匹配30帧，否则检查失败；发生时钟回退的样本单独计数并使亚秒判定失败。

`subsecond.softwarePass` 要求全部匹配的软件链路样本低于1000ms且没有负时差；
`continuityPass` 要求输出最大间隔低于1000ms；`joinPass` 要求 `first_frame_ms` 低于1000ms；
`pass` 要求三者同时满足。
这个字段是目标评估，不因目标未达成而把协议正确性检查伪装成通过目标。

只展示成功输出的帧，因此必须同时查看 dropped、freeze_ms、max_gap_ms 和恢复计数。
持续丢帧时，软件链路样本可能仍很低，而 continuityPass 会失败。
没有包含真实摄像头/屏幕采集或物理屏幕呈现，没有跨主机时钟同步，不能称为真实采集到显示延迟。
`first_frame_ms` 使用播放器单调时钟，从进入播放操作（连接、鉴权、目录、解码器启动之前）
计到首帧实际解码并完成软件输出；重连不重置计时。它不包含操作系统启动播放器进程的耗时。
无损链路的 deadline/FIFO 加入结果另外写入 `startup-report.json`。
播放器选定视频轨道后主动调用 `request_keyframe`，等待独立帧时继续通过已有控制层限频重试，
避免被动等待自然 GOP。发布方仍决定是否响应，不能据此保证所有源的首帧都低于一秒。

目标未达成的案例应保留原始报告，按 source_input/编码/收取/解码/输出阶段追查。
新增模块、编码器或策略不能替代这项验收，也不承诺任意网络条件下保证亚秒。

## 弱网模拟的排队边界

报告中的 `profile.queueModel=admitted-datagrams-v2` 表示只有实际接纳的数据报才占用串行发送时间。
排队数64、排队延迟250ms的上限仍然保留；超过上限的包立即丢弃，不累积虚假的后续带宽债务。
旧模拟器会给被拒绝的包继续累加时间，其结果不能与 v2 结果直接比较来宣称协议性能提升。

Relay 追踪包含 `relay_key_send`（帧大小及剩余预算）、`relay_drop`（过期、依赖缺失或发送槽满）、
`relay_start_failed` 和 `relay_send_failed`。结合 `encoder_response`、`key_received`、`key_decoded`
及 `frame_output` 定位恢复瓶颈；发送完成仍不等于解码完成。

## 实验：限制编码器关键帧突发

实时合成源支持 `PERI_MAX_INTRA_PCT=100` 或 `200`（默认 `0`，保留编码器原配置）。
该选项透传到 libaom 的 `aom-params=max-intra-rate`，仅作用于示例编码器；协议接入方可选择自己的策略。
FFmpeg 参数接口参考：https://ffmpeg.org/ffmpeg-codecs.html#libaom_002dav1 。
这是相对于平均帧码率的编码器软目标，不能作为严格的网络字节上限或帧大小保证；初始关键帧也可能明显超出。
超出目标后不能截断编码包，否则破坏解码；应继续按完整媒体对象和原有截止时间处理。

在设置 `PYTHONPATH=dist/live-python` 和合适的 `PERI_FFMPEG` 后，设置该变量并运行
`pnpm native:live:check`；报告 `maxIntraPct` 标识配置。未设置时仍为原有对照配置。
同一源30帧离线PSNR用于暴露画质代价，不能代替网络播放画质测量。
候选配置需同时查看 `freeze_ms`、恢复次数及最大间隔，多个短冻结仍影响体验。
此选项不改变控制层限频、Relay驻留预算或接收预算，也尚未解决跨应用的独立帧字节预算协商。

## 实验：恢复请求节流

实时示例支持 `PERI_RECOVERY_MS=300..1000`，默认1000；候选333需要与关键帧突发限制一起复测。
`adaptation::RecoveryPacer` 是可复用的恢复需求合并器，使用调用方单调时钟。
`request` 合并需求，`ready` 只判定是否允许响应，实际编码出独立帧后调用 `encoded`。
重复请求不会延长冷却，也不会重置源端保留的最早请求等待起点。
编码失败不能提前调用 `encoded`；应用仍需自行轮询反馈和驱动编码器。
码率切换保持其独立限制；缩短恢复冷却不保证每次关键帧都能通过受限链路。
该策略是应用层示例策略，不修改线协议，不要求第三方编码器采用相同冷却。

## Relay 的迟到失败处理

Relay 按每个订阅者、每条轨道保留接收端报告的最高已解码序号。
可丢弃对象发送失败不破坏参考链；失败序号已被解码报告覆盖，或属于新关键帧之前的旧GOP时，
不再因此清空参考链和请求关键帧。其余参考对象失败仍触发恢复。
报告代表接收端声明的实际解码进度，QUIC确认本身不被当作解码成功。
未发送报告的接入方继续使用保守恢复；接收端发来的显式关键帧请求仍照常转发。
该修复不改变公开接口、线协议或收发截止时间。

## 独立对象发送优先级

原生发送端为 `Object.independent=true` 的QUIC流设置优先级10，其余对象为0。
这使独立对象尚未发送的字节优先调度，不增加可用带宽，不撤回已发送的参考数据，也不放宽原有截止时间。
媒体层的关键帧、独立音频与目录沿用已有independent语义；第三方通过公共Object/Frame接口获得相同调度。
`relay_send_failed.reason` 区分 `ack_deadline` 与 `peer_cancelled`；
`object_receive_expired` 记录接收对象的本地驻留超时。
ACK截止失败不证明对端没收到，仍需结合接收、解码与输出追踪判读。

## 恢复期间的旧依赖对象

单视频播放器等待关键帧时使用recv_recovery，在头部校验后取消旧依赖对象。
这避免为不可用参考负载反复消耗读取预算。恢复阶段的独立对象仍要求完整负载和FIN。
播放器恢复读取默认最多300ms，并取协商maximum_ms的更小值；正常播放对象仍为150ms。
`PERI_RECOVERY_READ_MS=150`保留原预算对照，300启用对齐预算。亚秒验收阈值仍为1000ms。
`recovery_object_skipped`记录主动跳过，统计中的dropped包含这些对象；它们不等于新增网络丢包。
该接口不解决关键帧头部尚未到达、关键帧自身丢失或链路容量不足，弱网结果仍须实际验收。

## 严格验收命令

设置 `PERI_REQUIRE_SUBSECOND=1` 后，`native:live:check` 要求正常链路两次加入以及全部弱网轮次都通过亚秒条件。
任一组不通过时，在保存原始报告并完成资源释放检查后返回失败；默认0继续提供诊断性报告。
`PERI_NETWORK_REPEATS=1..5` 控制每种策略轮数，策略顺序逐轮轮换。
候选验收组合为 `PERI_RECOVERY_MS=333`、`PERI_MAX_INTRA_PCT=100`；不能将这一组合的结果归给默认配置。
该验收仍限于同机合成源的软件输入/输出与规定的UDP损伤模型；不等于物理屏幕测量或其他协议的性能对照。

`pnpm native:recovery:check` 提供严格候选验收入口，默认配置为恢复冷却333ms、
关键帧软目标100、恢复读取300ms、每种策略5轮，强制开启亚秒失败门禁。
仍需按实时源说明设置Python/PyAV与FFmpeg；参数可由环境覆盖并记录在报告中。
该命令的通过表示本次规定场景达标，不等于所有网络或全部生产场景的性能保证。

## 持续弱网与画质矩阵

`pnpm native:matrix:check` 串行执行 capacity、delay、loss、burst 四种配方。
默认同时比较关键帧限幅0与100，共8组；可用PERI_MATRIX_PROFILES与PERI_MATRIX_INTRA选择子集。
每组固定码率输入，目标931个真实解码输出帧；持续损伤60秒，要求首末输出覆盖至少60秒。
配方见 `scripts/network-profiles.ts`，延迟为下行单向附加延迟，非双向RTT。
随机丢包采用固定种子，重复运行可复现同包序列的随机决策；QUIC包序列受时序影响，不宣称逐包完全相同。
队列仍限制64包及250ms排队延迟，容量溢出产生的丢包计入lost；配置无随机丢包不代表零丢包。

报告新增freeze_count、freeze_ratio、output_fps和playback_ms。
freeze_ratio沿用gap>250ms时扣除正常67ms帧间隔的冻结定义，以首末输出间隔为分母，包含期间重连等待。
PSNR/SSIM对照使用同一原始合成画面、相同30帧输入，记录编码目标和关键帧参数；这是离线源画质，尚不等于丢帧后实际观看质量。
当前320×180、15fps合成源是控制变量素材，不能作为1080p/4K高画质的验收依据。
矩阵入口先收集所有配方结果，异常保留failure.json；返回0只表示诊断运行完成，应检查每组subsecond字段。

质量报告记录原始YUV的SHA-256，用于核对对照输入一致性。随机损伤在第10个输出帧后开始，首帧时间属于未损伤的加入阶段。

实时编码器另提供 `PERI_RATE_CONTROL=cbr` 候选，minrate/maxrate等于目标码率，bufsize为目标码率的1/5（200ms）。
默认vbr保留原行为；CBR参数未被编码器消费时直接报错。CBR与关键帧限幅仍是软编码目标，不保证逐帧硬字节上限。
质量和网络报告分别记录rateControl，比较时必须保持此配置可追踪。

`PERI_MATRIX_RATE_CONTROL=vbr,cbr` 可在同一串行矩阵中对照码率控制方式，默认只测vbr。
Relay在四个对象均等待确认时暂停出队，利用原有有界队列保留待发送参考帧；出队仍检查最初接收时间对应的截止。
这减少瞬时发送槽满引起的主动丢帧，队列大小、驻留上限及慢订阅者处理边界仍有效。

CBR候选尚不推荐：已测周期断网场景出现更高累计冻结，即使单次中断仍低于一秒。保持默认vbr，不能以源PSNR提高宣称端到端体验提高。
